## 一、背景 / 已确定（非本次新增）
- 形态：网页版（电脑端浏览器打开）+ 微信小程序版，二者共用同一套 JSON 数据模型，未来可互通。
- 网页版 v1 已写出 3 个文件：`web/index.html` / `web/styles.css` / `web/app.js`（周课表网格、课程增删改、localStorage 本地保存、导入/导出 JSON、自定义节次与星期数、学期名、单双周字段、配色、备注）。
- 用户最初特别要求的「拖动换课/调休」已在代码中补充（draggable + 拖放 + 占用互换逻辑）。

## 二、本轮结论（第 1 轮）
1. **课表数据来源**
   - 结论：以**手动录入**为主；用户后续会提供 **PDF 录入格式**，届时再做导入。
   - 理由：当前模型读不了图片，图片/扫描件自动解析暂不可行；PDF 若为文本型可后续抽取，扫描型仍受限。先手动录入不让进度卡住。
2. **小程序版**
   - 结论：**先网页版跑顺，小程序后做**（复用同一数据模型）。
   - 理由：网页版已成型，先验证好用再扩展，降低一次性复杂度。
3. **拖动交互**
   - 结论：**移动 + 互换**（拖到空格=移动；拖到已有课的格子=两门课对调时间，对应调休）。
   - 理由：与用户最初诉求一致；当前实现即此逻辑。
4. **节次时间显示**
   - 结论：每格显示「第N节」，**下面用小字备注具体时间**（如 08:00–08:45）。
   - 理由：用户要求；需新增每节对应的时间字段（可编辑）。

## 二之补补、时间表校历规则修正（2026-10-28 补充）
7. **默认时间表（校历）**
   - 结论：每**大节 = 两小节（45 分钟/小节）+ 大节内休息 10 分钟 = 100 分钟**；**大课（大节）之间休息 20 分钟**；**当天 17:10 收工，不排晚课**。
   - 详细：4 大节起始 08:00 / 10:00 / 13:30 / 15:30；默认 **8 小节**（=4 大节）对应。小节时间表：
     ```
     08:00–08:45 | 08:55–09:40 | 10:00–10:45 | 10:55–11:40
     13:30–14:15 | 14:25–15:10 | 15:30–16:15 | 16:25–17:10
     ```
   - 理由：用户明确校历——大课之间休息 20 分钟、只上到 17:10。据此修正默认生成逻辑（此前为 12 节且含晚课，已弃用）。
   - 实现：`app.js` 的 `genDefaultTimes()` 重写为按 4 大节规则生成；`defaultConfig().sections` 改为 8。设置弹窗仍可按行逐节编辑。
   - 注意：若用户手动把节次改成 >8，超出 4 大节部分按「晚上单小节接力（19:00 起）」兜底，避免时间溢出；默认场景不触发。

## 二之补、本轮结论（第 2 轮）
5. **节次时间表**
   - 结论：提供**默认值且可设置**。规则：8:00 上第 1 节；每小节课 45 分钟、中间休息 10 分钟；两小节组成一节课（一大节约 100 分钟）；13:30 上下午第 1 节。
   - 理由：用户给出具体校历规则；据此生成默认时间表，并放进设置里可逐节编辑。
   - 数据模型：新增 `config.sectionTimes`（字符串数组，如 `"08:00–09:40"`），长度随节次数。
6. **上课前提醒**
   - 结论：**以后再做**，不纳入网页版 v1。
   - 理由：当前阶段先把课表本身做扎实；提醒依赖浏览器通知且关页面即失效，价值有限，延后。

## 二之补补补、课表粒度（大节/小节）可切换（2026-10-28 补充）
8. **课表粒度（大节 / 小节）**
   - 结论：**默认 4 大节**（每格一大节，100 分钟）；设置里提供「大节 / 小节」下拉可切换，并自动填入对应节次数与时间预设，用户仍可手动微调节次/时间。
   - 理由：用户要求默认大节、且可在设置里调整。
   - 实现：
     - `config.classMode`（`'big' | 'small'`），默认 `'big'`；`defaultConfig().sections = 4`，`sectionTimes = genBigTimes()`。
     - 新增 `genBigTimes()`：4 大节 = `[08:00–09:40, 10:00–11:40, 13:30–15:10, 15:30–17:10]`。
     - 设置弹窗新增 `sMode` 下拉；切到 big→预填 4 格+大节时间，切到 small→预填 8 格+小节时间。
     - 切换粒度保存时，按比例重映射已有课程节次（big→small: 第b大节→第2b-1~2b小节；small→big: 取 ceil(小节/2) 大节），避免错位。
     - 课表左侧行标题：big 显示「第N节」（中文数字，如「第一节」），下方含两行小节时间（由 `deriveSmallTimes()` 从大节时间推导，各占一盒）；small 显示「第N节」+ 单行时间。
   - 默认大节时间表与左侧显示（big 模式）：
     ```
     第一节（大节格拉长，内含两行）
       08:00–08:45
       08:55–09:40
     第二节
       10:00–10:45
       10:55–11:40
     第三节
       13:30–14:15
       14:25–15:10
     第四节
       15:30–16:15
       16:25–17:10
     ```
   - 大节模式行高加大（`.grid.bigmode td.cell { height: 118px }`）并加宽左侧列（88px），更美观。
   - 显示细节：大节视图下，每个大节左侧行标题内**拆出两行小节时间**（由大节时间推导：小节1=起~起+45，小节2=起+55~起+100）。例如第1大节内显示 `08:00–08:45` 与 `08:55–09:40`。新增 `deriveSmallTimes()` 从大节时间串解析出两小节。

## 八、PDF 导入选型（architect，2026-10-28）
12. **「导入 PDF」失败根因**
    - `xskb.pdf` 为图片型 PDF（0 文字层）+ 跨两页 + 课表含「跨大节合并单元格」。
    - 浏览器内 pdf.js 取不到文字层 → 降级 OCR（tesseract.js + chi_sim，需联网下几十 MB 模型）；启发式网格重建对这种版面极易错位/失败 → 用户点「导入 PDF」无果。
13. **方案对比与推荐**
    - 方案 A（推荐，现在用）：AI（视觉/OCR）读 PDF → 生成 app 的 JSON → 用户「导入JSON」。零网络/部署依赖、100% 进本地、由人工核对兜底。风险仅为换表需再来一次。
    - 方案 B：把浏览器内「导入 PDF」按钮打磨（报错提示 + 核对弹窗体验）。保留纯本地隐私，但仍依赖 CDN 下 OCR 模型，对跨页合并格版面仍可能需手改。
    - 方案 C：云端 OCR 服务（腾讯云/百度 OCR 或 Cloudflare Worker）。解析最稳但需部署/密钥/费用，维护成本不匹配需求，**暂不推荐**。
    - 决定作用理由：方案 A 是唯一不依赖脆弱浏览器 OCR、且用户当天即可把真课表装进去的路径。
14. **已产出**：`课表应用/课表数据.json`（14 门课，4 大节，周次范围 5-8/1-16/1-11/1-8/1-10/1-12 等已保留）。两处教师名 OCR 摇摆（宋野/宋辉、张琪琪/张琪瑶），已写 note 提示，导入后可在编辑器改。待用户确认后正式生效（并视需要走方案 B 打磨按钮）。

## 九、PDF→JSON 自动化选型（architect，2026-11-16）
15. **新需求**：用户要「自动 PDF 转 JSON」，不再每次找 AI 看图手转。约束：中国大陆；桌面网页版优先、将来出微信小程序版且共用一套 JSON；网页上点「导入PDF」按钮自动转换、尽量无人值守；转换后端放云端、接受课表上传；样本仍是 `xskb.pdf`（2 页扫描件、无文字层、跨大节合并格）。
16. **冲突说明**：「纯浏览器 OCR + 无人值守」不可兼得——jsdelivr 连不上，且启发式网格重建对跨页合并格易错位。故把问题改成「网页按钮背后的活儿交给谁干」，用户选云 OCR。
17. **现查事实（官方页）**：腾讯云表格识别 V3 = `RecognizeTableAccurateOCR`，Version `2018-11-19`，域名 `ocr.tencentcloudapi.com`；支持 PNG/JPG/JPEG/BMP/PDF，Base64 后 ≤10M，建议 ≥600×800、长短边比 <3；PDF 仅单页、用 `PdfPageNumber` 逐页调用；返回每格 `ColTl/ColBr/RowTl/RowBr` 合并坐标，`UseNewModel=true` 提升复杂表格还原；默认 2 次/秒。免费额度：表格识别 V2/V3 共享 1000 次/月（每月 1 号发放、当月有效）；按量 0.15/0.10/0.06 元/次三档，资源包 1000 次 120 元。腾讯云与微信小程序同生态，云开发云函数可转发且前端不暴露密钥。
    - 来源：https://cloud.tencent.com/document/product/866/86721 、https://cloud.tencent.com/developer/article/2747492 、https://cloud.tencent.com/developer/article/2740949
18. **方案对比**：
    - A（推荐）：腾讯云表格识别 V3 + 专用转换页，网页直调（签名走轻量后端/云函数），把单元格坐标映射成课表 JSON。2 页 = 2 次调用，免费额度内。风险：密钥不可写死前端、有跨域需转发层、合并格仍需少量核对。
    - B：A + 云开发 SCF 一键转发（上传→识别→归一 JSON→回传），网页与小程序共用同一函数，密钥锁云端。比 A 多配云开发环境，但最贴合「网页按钮 + 小程序共用」。
    - C：本地脚本 + AI 视觉，数据不出本机；与用户选的云端相反，且需装本地渲染库、仍难无人值守，不推荐。
19. **决定作用理由**：用户同时要「云 OCR + 无人值守 + 网页按钮」，A 是满足三条的最短路径，且 V3 原生支持 PDF 与合并单元格、每月 1000 次免费可零成本试错。B 不是必需，仅在小程序端也要同一按钮且不愿两端各存密钥时才升级。
20. **待用户提供**：腾讯云 SecretId/SecretKey（控制台→访问管理→API 密钥管理，授予文字识别权限），放环境变量或云函数环境变量，绝不写死代码。用户说「开始」后再动手。


## 十、多课表（学期切换）选型（2026-11-23）
21. **需求**：顶栏「📅 我的课表」标题 + 「2026 秋季学期」输入框合并成一个下拉按钮（放第一行中间），点开切换课表、末行「新建课表」；每个学期一张独立课表，课程/学期名/节次等设置/当前周全部独立；「清空」按钮改成「删除当前课表」。新建=空白表+默认设置。
22. **约束**：中国大陆、桌面网页为主、将来小程序版共用数据；数据全本地 localStorage；用户为 AI 新手，网络受限；预览面板 iframe 会吞原生弹窗（已改应用内确认框）、会缓存（已加 no-store）。
23. **方案 A（推荐，已选）**：单键 `localStorage['schedule.v2'] = { tables:[{id,name,config,courses,view}], activeId }`。切换=改 activeId 后 load/render；旧 `schedule.v1` 首次自动迁移成第一张表。读写集中一个函数，改 load/save + 顶栏即可，渲染逻辑不动。

25. **默认细节**：学期名改名入口放 ⚙ 设置弹窗（加「课表名称」字段）；删除保护——至少留一张表，删最后一张改为「清空该表课程」。
